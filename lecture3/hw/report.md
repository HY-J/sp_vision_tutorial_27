## 1. 图像生命周期与所有权

解释本项目中图像源为什么会复用缓冲区，以及 `cv::Mat` 的普通复制对底层像素数据
意味着什么。说明你的修改让一个 `Frame` 在进入队列后拥有什么，并解释为何后续读取
不会再改变它。

图像源复用内部缓冲区是为了模拟真实相机的硬件帧缓存模式：固定一块内存重复写入，无需频繁分配像素内存，保持内存占用稳定。

`cv::Mat` 的普通赋值是**浅拷贝**：只复制矩阵头和数据指针，底层像素内存共享。原代码直接将 `buffer_` 赋值给 `frame.image`，导致入队的帧与源缓冲区共用同一块像素内存。producer 读取下一帧时会覆盖这块内存，造成队列中旧帧数据损坏、校验失败。

修复时使用 `buffer_.clone()` 做**深拷贝**：重新分配独立的像素内存并完整复制数据。入队后的 `Frame` 拥有完全独立的图像数据所有权，后续缓冲区的覆写操作不会影响已入队的帧。

## 2. 并发处理与恰好一次

结合 `BlockingQueue` 的 `push`、`pop` 和 `close` 行为，解释多个 worker 如何分工。
为什么你的实现既不会漏掉已经入队的帧，也不会重复处理同一帧？输入耗尽时，正在等待
以及仍在处理数据的 worker 分别会怎样？

`BlockingQueue` 的三个核心行为：
  `push`：线程安全地将帧放入队尾
  `pop`：原子地从队首取帧，队列为空则阻塞等待，同一帧只会被一个线程取到
  `close`：关闭队列，唤醒所有阻塞的 `pop` 调用，后续 `pop` 直接返回 false

**不重不漏的原因**：`pop` 内部有互斥锁保护，是原子操作，多线程并发取帧时，同一帧只会被恰好一个 worker 取出；所有入队的帧都会被依次消费，不会丢弃。

**输入耗尽时的行为**：
  正在等待 `pop` 的 worker：队列关闭后立即被唤醒，`pop` 返回 false，退出循环
  正在处理帧的 worker：完成当前帧处理后，下一次 `pop` 发现队列关闭，退出循环

## 3. 共享统计数据

指出哪些线程会读写 `Statistics`。解释原实现中的竞争为什么可能导致错误结果，并说明
你的同步方案提供了什么保证。还应说明取得快照时为什么是安全的。

producer 线程写 `produced` 计数；每个 worker 线程写 `processed`、`saved`、`corrupted` 计数；主线程读取统计快照。

**原实现的问题**：普通整型的自增不是原子操作，会拆分为 "读 - 改 - 写" 三步。多线程并发时，多个线程可能读到同一个旧值，各自加 1 后写回，导致计数丢失；读取快照时也可能读到半新半旧的不一致状态。

**同步方案**：为所有统计操作加 `std::mutex` 互斥锁，使用 `std::lock_guard` 自动加解锁。保证：
1. 计数更新串行执行，不会丢失
2. 快照读取全程加锁，四个值来自同一时刻，逻辑一致
3. 异常时自动解锁，不会死锁

### 为什么快照是安全的
获取快照时同样持有互斥锁，在锁释放之前，没有其他线程可以修改任何计数器。因此返回的四个统计值都来自同一个一致的状态，不会出现 "生产数是新的、处理数是旧的" 这种逻辑矛盾的快照。

## 4. 线程关闭协议

分别描述以下两条路径中的事件顺序，并解释为什么不会发生 `std::terminate`、悬空访问
或永久等待：

1. 调用者执行 `start()` 后显式调用 `wait()`；
2. 调用者执行 `start()` 后不调用 `wait()`，直接让 `Pipeline` 析构。

如果你的实现允许某个生命周期方法被重复调用，也请说明其行为；如果不允许，请说明前置条件。

### 路径 1：start () 后调用 wait ()
1. 调用 `start()`：依次启动所有 worker 线程，再启动 producer 线程，函数立即返回。
2. producer 运行：不断读取图像、更新生产计数、将帧推入队列；所有图像读取完毕后，调用 `queue.close()` 关闭队列，随后 producer 线程执行完毕。
3. worker 运行：不断从队列 `pop` 帧、处理、保存、更新统计；当队列为空时阻塞等待，当队列关闭且为空时，`pop()` 返回 false，worker 退出循环，线程结束。
4. 调用 `wait()`：先等待 producer 线程 join 回收，再依次等待每个 worker 线程 join 回收；所有线程都退出后，`wait()` 返回。

**安全性**：
  队列正常关闭，worker 都会正常退出，不会永久等待；
  所有线程都被显式 join 回收，`std::thread` 对象不会处于 joinable 状态销毁，不会触发 `std::terminate`；
  线程全部退出后，成员变量才会被销毁，不会出现线程访问已销毁对象的悬空访问。

### 路径 2：不调用 wait ()，直接析构 Pipeline
1. Pipeline 对象进入析构函数。
2. 第一步立即调用 `queue.close()`：关闭队列，唤醒所有阻塞在 `pop()` 的 worker 线程，让它们可以退出循环。
3. 第二步 join producer 线程：如果 producer 还在运行，等待它执行完毕；如果已经结束则直接跳过。
4. 第三步循环 join 所有 worker 线程：逐个等待每个 worker 退出，确保所有工作线程都完全停止。
5. 所有线程回收完成后，析构继续，成员变量（队列、统计、配置等）自动销毁。

**安全性**：
  析构首先关闭队列，所有阻塞的 worker 都会被唤醒并退出，不会一直卡在 `pop()`。
  所有线程对象都在析构中被 join，销毁时都处于非 joinable 状态，符合 C++ 标准,不会触发 `std::terminate`。
  先等待所有线程退出，再销毁成员变量，此时没有线程还在访问这些成员，不会出现野指针访问。

`wait()` 支持重复调用：内部每次 join 前都会判断 `joinable()`，已经 join 过的线程不会重复 join，重复调用 `wait()` 是安全的，不会报错。
析构函数只会被调用一次，不存在重复调用的问题；但即使之前已经调用过 `wait()`，析构里的逻辑依然安全，因为已经 join 过的线程 `joinable()` 为 false，会直接跳过。
